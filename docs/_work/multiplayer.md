## Two competing designs

| | Stack A: `Assets/Networking/` (namespace `GravityWars.Networking`) | Stack B: `Assets/Multiplayer/` (namespace `GravityWars.Multiplayer` + global classes) |
|---|---|---|
| Model | Server relays *actions* (fire angle/power/perk slot); clients "replay deterministically" — but every `ClientRpc` body is empty / a log (`MatchManager.FireMissileClientRpc`, `MoveShipClientRpc`, `ActivatePerkClientRpc`, `RoundEndClientRpc`, `MatchEndClientRpc`; `NetworkedPlayerShip.TakeDamageClientRpc`, `OnHealthChanged`…) | Deterministic lockstep: server owns a turn state machine (`NetworkTurnCoordinator`), relays input structs (`NetworkInputManager`), clients spawn identical planets from a seed (`GameManagerNetworkAdapter.GenerateDeterministicPlanets` → `GameManager.SpawnPlanetsWithSeed/GetSpawnedPlanetData/SpawnPlanetsFromNetworkData`) and ships at fixed ±25 x positions |
| Match rules | `MatchManager`: turn timeout 60 s, "just end match after 1 round" (line 397-398) | `NetworkTurnCoordinator`: prep 3 s, turn 15 s, missile flight max 30 s, `winningScore 3`, loser starts next round; `NetworkGameManager`: **real-time** rounds (`roundDuration 180 s`, `respawnDelay 3 s`, "most health wins on timeout", `roundsToWin 3`) — a third, non-turn-based rule set inside stack B itself |
| Rewards | none | `NetworkGameManager.AwardMatchRewards`: win 500 credits / 10 gems / 1000 XP, loss 200 / 0 / 500, +50 credits & +100 XP per kill, BP XP 100/50 — applied **on the client** in `AwardRewardsClientRpc` via `ProgressionManager` (fourth reward table, see economy.md) |
| GameManager integration | `OnlineGameAdapter` (RequireComponent GameManager) exposes `OnPlayerFireMissile/OnPlayerMove/OnShipTakeDamage/OnTurnStart/OnTurnEnd/OnShipDestroyed/OnMatchEnd` — **GameManager never calls any of them** (rg) | `GameManager` has the matching hooks (`OnNetworkPlayersAssigned`, `OnNetworkTurnStateChanged`, `ExecuteNetworkFireAction/MoveAction`, `OnNetworkMissileDestroyed`, `OnNetworkScoreUpdated`, `OnNetworkRoundEnd`, `OnNetworkMatchEnd`, lines 1839-1927) delegating to `GetComponent<GameManagerNetworkAdapter>()`; `PlayerShip.ApplyNetworkRotation` (711) and `ExecuteNetworkFire` (725) exist |
| Connection | `NetworkService` (Relay via `Unity.Services.Relay`, UTP `SetRelayServerData`, "dtls"), driven by `LobbyManager` (UGS Lobby quick-match/create/join-by-code, heartbeat 15 s, relay code stored in lobby data `RelayCode`) | `ConnectionManager` (Relay with 3 retries, or local `127.0.0.1:7777`), no lobby |
| UI | `OnlineMatchmakingUI` (partially guarded; shows "requires Netcode package" error when define off), `LobbyUI` (ready button is local-only, match starts on player count ≥ 2 after 3 s, loads scene **"HotSeat"**), `ConnectionStatusUI` (ping colours 50/100/150 ms) | none (OnGUI debug overlays in `NetworkTurnCoordinator`, `NetworkInputManager`, `NetworkedPlayerShip`) |
| Determinism | claims it, does nothing to ensure it | relies on identical inputs + Unity physics (`Missile3D` uses a `Rigidbody`, gameplay-physics.md) with no state hash / resync — floating-point drift between machines is not handled |

Both stacks expect `GameManager`, planets and ships from the hotseat scene; neither has a scene, prefab with `NetworkObject`, or `NetworkManager` component set up (scene YAML scan: no networking components in any scene).

## Other online pieces
- `Online/MatchmakingService` (unguarded, plain singleton, not in a scene): ELO-window matchmaking with an in-memory queue and `OnMatchFound` event nobody subscribes to (see battlepass-ranked.md). It never talks to Lobby/Relay.
- `Online/MatchHistoryManager` (guarded): records `MatchResult` to Cloud Save with a "TEMPORARY: Synchronous wait for async operation" (lines 402-443).
- Documentation intent: `Documentation/Implementation Plan.md` ("Online-First Approach", Phase 1 "Install Netcode… set up scripting define symbols", Phase 2 "Complete end-to-end online match") and the old GDD ("Peer-to-peer netcode – both clients identical, server validates"). Code matches the *intent* of stack B more closely than stack A.

## Bugs / risks (N)

| ID | Sev | Where | Problem | Suggested fix |
|---|---|---|---|---|
| N1 | high | all guarded files | Enabling `UNITY_NETCODE_GAMEOBJECTS` produces compile errors in ~10 files (missing `using`s, missing `GameManager.StartGamePhase/StartPlayerTurn`, missing `NetworkedPlayerShip.IsDead/Respawn/GetHealth/OnDeath`). The define is the only thing keeping the project compiling. | Decide on one stack (recommendation below), delete the other, restore the `using` lines, compile with the define on in a branch before touching gameplay. |
| N2 | high | `Networking/` vs `Multiplayer/` | Two incompatible architectures for the same feature, plus a third rule set (real-time rounds with respawn) inside `NetworkGameManager`. | Keep stack B's lockstep design (`NetworkTurnCoordinator` + `NetworkInputManager` + `GameManagerNetworkAdapter` + `NetworkMessages`) because `GameManager`/`PlayerShip` already have its hooks; keep `LobbyManager` + `NetworkService` from stack A for UGS lobby/relay; delete `MatchManager`, `NetworkedPlayerShip`, `OnlineGameAdapter`, `NetworkGameManager`, `ConnectionManager`. |
| N3 | high (design) | stack B | No determinism safeguards: `Missile3D` moves a `Rigidbody`; PhysX results differ across CPUs/frame-rates. Lockstep without a periodic state hash + host-authoritative correction will desync silently. | Either simulate missiles with the custom integrator only (same code the preview and bot use — see BOT2) and fixed timestep, or make the host authoritative and stream missile transforms (`NetworkTransform`). Record decision in GDD. |
| N4 | medium | `NetworkGameManager.AwardRewardsClientRpc` | Rewards computed on the server but applied by the client to its own `ProgressionManager` with hard-coded amounts that contradict `GameManager.AwardMatchProgression`. | One reward table (config asset) used by the local path; server sends the *result*, client applies through the same `AwardMatchProgression` code. |
| N5 | medium | `LobbyUI.StartMatch` (line 351), `OnlineGameAdapter.ReturnToLobbyCoroutine` (343) | Loads `"HotSeat"` (the stale scene, not in Build Settings) and `"MainMenu"` (the old menu). | Scene names from one config; see ui-screens.md for the scene decision. |
| N6 | medium | `LobbyUI.OnReadyButtonClicked`, `CheckIfBothPlayersReady` | Ready state is never written to lobby data; match starts when 2 players are present. `Update()` polls with `Time.frameCount % 120` (frame-rate dependent). | Use lobby player data + Lobby events/polling with a timer. |
| N7 | medium | `NetworkTurnCoordinator._currentTick`, `NetworkInputManager._currentTick` | Each peer increments its own tick from `Update`; ticks in messages are not comparable, so "fire on the same tick" is not achieved. | Server-issued tick / turn sequence number. |
| N8 | medium | `NetworkInputManager.ValidateFireAction/ValidateMoveAction` | Always `return true` (TODO). `IsOwner` checks on a scene-placed `NetworkBehaviour` are meaningless (owner = server). | Validate through `NetworkTurnCoordinator.ValidatePlayerAction(senderId)` using `ServerRpcParams`. |

| N10 | low | `NetworkTurnCoordinator.OnGUI`, `NetworkInputManager.OnGUI`, `NetworkedPlayerShip.OnGUI` (editor only) | Debug overlays always drawn when spawned (allocations every frame). | `#if DEVELOPMENT_BUILD`/debug flag. |

## Open questions for the GDD
1. Which network architecture (lockstep with custom deterministic physics vs host-authoritative)? Recommendation: host-authoritative turn state + deterministic custom missile integrator (N3), because the game already has that integrator in three places.
2. Is online PvP part of the vertical slice? Code and docs say "online-first", but nothing runs. Recommendation: hotseat + bot slice first, online as a later milestone (see GDD Implementation Plan).
3. Should `MatchmakingService` (ELO queue) survive, given UGS Lobby quick-match does the matching? Recommendation: keep only the ELO window rule as a lobby filter.
